Aggregate Function

Fungsi yang merangkas banyak baris menjadi satu nilai. Inti dari hampir semua soal analitik — selalu dipasangkan GROUP BY dan disaring HAVING.

Lima fungsi wajib hafal

FungsiKegunaanPerilaku NULLContoh Konteks
COUNT(*)Hitung semua baris termasuk NULLTidak peduli NULLTotal semua order
COUNT(kolom)Hitung baris non-NULL pada kolomSkip NULLTotal order yang ada customer-nya
SUM(kolom)Jumlahkan nilai numerikNULL diabaikanTotal revenue
AVG(kolom)Rata-rata nilai non-NULLPembagi = baris non-NULLRata-rata harga produk
MIN / MAXNilai terkecil / terbesarAbaikan NULLProduk termurah/termahal

Urutan eksekusi SQL — ini sering ditanya di essay

#KlausaKapan jalanBoleh pakai aggregate?
1FROM / JOINTentukan tabel & gabungkan✗ Tidak
2WHEREFilter baris mentah✗ Tidak (error)
3GROUP BYKelompokkan baris✗ Tidak
4HAVINGFilter kelompok✓ Ya (wajib di sini)
5SELECTPilih & hitung kolom✓ Ya
6ORDER BYUrutkan hasil✓ Ya
7LIMITBatasi baris output✗ Tidak

Contoh query lengkap — laporan penjualan per kategori

SQL
SELECT k.nama_kategori, COUNT(p.produk_id) AS jumlah_produk, -- hitung produk per kategori AVG(p.harga) AS rata_harga, -- rata-rata harga MAX(p.harga) AS harga_tertinggi, SUM(oi.qty) AS total_terjual -- total unit terjual FROM kategori k JOIN produk p ON p.kategori_id = k.kategori_id LEFT JOIN order_items oi ON oi.produk_id = p.produk_id -- LEFT agar produk belum terjual tetap muncul LEFT JOIN orders o ON o.order_id = oi.order_id AND o.status = 'COMPLETED' -- filter di ON clause, bukan WHERE GROUP BY k.kategori_id, k.nama_kategori HAVING COUNT(p.produk_id) >= 2 -- hanya kategori dengan min 2 produk AND AVG(p.harga) > 300000 -- dan rata-rata harga > 300rb ORDER BY total_terjual DESC, rata_harga DESC;
Kenapa filter di ON clause bukan WHERE? Kalau o.status = 'COMPLETED' ditaruh di WHERE, LEFT JOIN jadi berperilaku seperti INNER JOIN — produk tanpa order COMPLETED akan hilang dari hasil. Di ON clause, filter hanya mempengaruhi pasangan JOIN, bukan mengeliminasi baris kiri.
Jebakan UAS #1: Soal "tampilkan X yang Y-nya di atas rata-rata" → HAVING + AVG. Soal "filter status sebelum aggregate" → WHERE. Kalau kondisi punya aggregate function, 100% HAVING.
02 · Materi Inti

Subquery

Query di dalam query. Bisa di SELECT, FROM, WHERE, HAVING, atau setelah IN/EXISTS. Wajib bisa bedain correlated vs non-correlated.

Empat jenis subquery

Non-Correlated
  • Dieksekusi 1 kali saja
  • Tidak merujuk kolom tabel luar
  • Hasilnya bisa di-cache
  • Performa: O(1) kali eksekusi
Correlated
  • Dieksekusi per baris tabel luar
  • Merujuk kolom dari query luar
  • Tidak bisa di-cache
  • Performa: O(n) kali eksekusi

Non-Correlated — dieksekusi sekali, hasilnya dipakai berulang

SQL
-- Produk yang harganya di ATAS rata-rata seluruh produk -- Subquery AVG(harga) dieksekusi SEKALI → hasilnya misal 356000 -- Query luar tinggal bandingkan harga > 356000 SELECT nama_produk, harga, harga - (SELECT AVG(harga) FROM produk) AS selisih_dari_rata FROM produk WHERE harga > (SELECT AVG(harga) FROM produk) ORDER BY selisih_dari_rata DESC; -- IN: produk yang pernah terjual dalam order COMPLETED SELECT nama_produk FROM produk WHERE produk_id IN ( SELECT DISTINCT oi.produk_id FROM order_items oi JOIN orders o ON o.order_id = oi.order_id WHERE o.status = 'COMPLETED' );

Correlated — referensi ke outer query, jalan ulang tiap baris

SQL
-- Customer yang total belanjanya di atas rata-rata semua customer -- Subquery dalam dijalankan ULANG untuk tiap baris c (tiap customer) SELECT c.nama, c.kota FROM customers c WHERE ( -- subquery ini BERGANTUNG pada c.customer_id dari outer query SELECT COALESCE(SUM(o.total_harga), 0) FROM orders o WHERE o.customer_id = c.customer_id -- ← referensi outer! AND o.status = 'COMPLETED' ) > ( -- subquery rata-rata: non-correlated, dieksekusi SEKALI SELECT AVG(total_per_c) FROM ( SELECT SUM(total_harga) AS total_per_c FROM orders WHERE status = 'COMPLETED' GROUP BY customer_id ) sub );
Cara deteksi correlated: cek apakah subquery punya kolom yang berasal dari tabel di query luar. Di sini c.customer_id berasal dari tabel customers c di luar. Kalau ada → correlated.

EXISTS vs IN — kapan pilih yang mana

SQL
-- EXISTS: lebih efisien untuk dataset besar, berhenti di baris pertama -- Pertanyaan: "ada atau tidak ada?" — hasilnya hanya TRUE/FALSE SELECT c.nama FROM customers c WHERE EXISTS ( SELECT 1 -- nilai 1 tidak penting, yang penting ada baris atau tidak FROM orders o WHERE o.customer_id = c.customer_id AND o.status = 'COMPLETED' ); -- NOT EXISTS: produk yang belum pernah terjual sama sekali -- LEBIH AMAN dari NOT IN ketika kolom bisa mengandung NULL SELECT p.nama_produk, p.stok FROM produk p WHERE NOT EXISTS ( SELECT 1 FROM order_items oi WHERE oi.produk_id = p.produk_id ); -- Kenapa NOT EXISTS lebih aman dari NOT IN? -- NOT IN (1, 2, NULL) → SELALU FALSE karena NULL tidak bisa dibandingkan -- NOT EXISTS tidak punya masalah NULL ini

Derived Table — subquery di FROM, jadi "tabel sementara"

SQL
-- Cari customer dengan ranking belanja (tanpa window function) -- Langkah 1: hitung total per customer dulu di subquery -- Langkah 2: query luar baru pakai hasilnya untuk filter/sort SELECT rk.nama, rk.total_belanja, rk.rank_belanja FROM ( SELECT c.nama, SUM(o.total_harga) AS total_belanja, RANK() OVER (ORDER BY SUM(o.total_harga) DESC) AS rank_belanja FROM customers c JOIN orders o ON o.customer_id = c.customer_id WHERE o.status = 'COMPLETED' GROUP BY c.customer_id, c.nama ) rk -- alias wajib ada untuk derived table WHERE rk.rank_belanja <= 3 -- ambil top 3 customer ORDER BY rk.rank_belanja;
Jebakan UAS #2: Soal "tampilkan data di atas rata-rata grupnya sendiri" → correlated subquery atau window function. Kuncinya ada kata "rata-rata per kategori / per grup" bukan rata-rata semua.
03 · Materi Inti

Trigger

Kode yang otomatis jalan saat INSERT/UPDATE/DELETE terjadi. Tidak dipanggil manual — reaktif terhadap event tabel.

Anatomi lengkap trigger

KomponenPilihanArti & Kapan Pakai
TimingBEFORE / AFTERBEFORE: validasi & cegah data masuk. AFTER: aksi turunan (update tabel lain, logging)
EventINSERT / UPDATE / DELETETrigger bereaksi pada operasi mana
LevelFOR EACH ROWJalan sekali per baris yang terdampak (MySQL hanya punya ini)
NEWINSERT, UPDATENilai baris baru / setelah diubah. Bisa dimodifikasi di BEFORE INSERT/UPDATE
OLDUPDATE, DELETENilai baris sebelum diubah/dihapus. Read-only
SIGNALSQLSTATE '45000'Lempar error custom → batalkan operasi yang memicu trigger

BEFORE INSERT — validasi stok berlapis sebelum order masuk

SQL
DELIMITER $$ CREATE TRIGGER trg_validasi_order_items BEFORE INSERT ON order_items FOR EACH ROW BEGIN DECLARE v_stok INT; DECLARE v_harga DECIMAL(12,2); -- Ambil stok & harga dari tabel produk SELECT stok, harga INTO v_stok, v_harga FROM produk WHERE produk_id = NEW.produk_id; -- Validasi 1: produk harus ada IF v_stok IS NULL THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Produk tidak ditemukan'; END IF; -- Validasi 2: qty harus positif IF NEW.qty <= 0 THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Qty pesanan harus lebih dari 0'; END IF; -- Validasi 3: stok mencukupi IF NEW.qty > v_stok THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Qty pesanan melebihi stok tersedia'; END IF; -- Normalisasi: pastikan harga_satuan sesuai dengan harga di tabel produk -- (modifikasi NEW hanya bisa dilakukan di BEFORE trigger) SET NEW.harga_satuan = v_harga; END$$ DELIMITER ;

AFTER UPDATE — restore stok otomatis saat order di-cancel

SQL
DELIMITER $$ CREATE TRIGGER trg_restore_stok_on_cancel AFTER UPDATE ON orders FOR EACH ROW BEGIN -- Hanya proses jika status berubah PENDING → CANCELLED -- OLD.status = nilai sebelum UPDATE, NEW.status = nilai setelah UPDATE IF OLD.status = 'PENDING' AND NEW.status = 'CANCELLED' THEN -- Kembalikan stok semua produk dalam order ini sekaligus UPDATE produk p JOIN order_items oi ON p.produk_id = oi.produk_id SET p.stok = p.stok + oi.qty WHERE oi.order_id = NEW.order_id; -- Catat ke log (OLD & NEW tersedia di body trigger) INSERT INTO order_log (order_id, aksi, old_status, new_status, keterangan, waktu) VALUES ( NEW.order_id, 'CANCEL_RESTOCK', OLD.status, NEW.status, CONCAT('Stok dikembalikan. Refund: Rp ', FORMAT(NEW.total_harga, 0)), NOW() ); END IF; END$$ DELIMITER ;
Jebakan UAS #3: "Cegah data invalid" → BEFORE (data belum masuk, masih bisa ditolak). "Lakukan aksi setelah data berubah" → AFTER. Salah pilih timing = trigger tidak bisa menjalankan tujuannya.

SQL Transaction

Sekumpulan operasi SQL yang dianggap satu unit — semuanya berhasil atau semuanya dibatalkan. Fondasi dari properti ACID.

ACID — hafal definisi + contoh kasusnya

HurufPropertiDefinisiContoh Pelanggaran
AAtomicitySemua langkah sukses, atau tidak ada yang tersimpan sama sekaliStok berkurang tapi order tidak terbuat
CConsistencyDB berpindah dari satu state valid ke state valid lainTotal stok di inventory ≠ total di order_items
IIsolationTransaksi concurrent tidak saling melihat perubahan yang belum di-commitDua user beli produk terakhir secara bersamaan
DDurabilitySetelah COMMIT, perubahan permanen meski server matiData order hilang setelah server crash

Transaction dengan error handling penuh — pola production

SQL · Stored Procedure
DELIMITER $$ CREATE PROCEDURE sp_checkout( IN p_customer_id INT, IN p_produk_id INT, IN p_qty INT, OUT p_order_id INT -- kembalikan ID order ke pemanggil ) BEGIN DECLARE v_harga DECIMAL(12,2); DECLARE v_stok INT; DECLARE v_total DECIMAL(12,2); -- EXIT HANDLER: jika SQL error apapun terjadi → rollback otomatis DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN ROLLBACK; RESIGNAL; -- teruskan error ke pemanggil END; -- Ambil data produk + kunci baris (FOR UPDATE = pessimistic lock) -- Ini mencegah race condition saat 2 user checkout produk yang sama SELECT harga, stok INTO v_harga, v_stok FROM produk WHERE produk_id = p_produk_id FOR UPDATE; -- Validasi sebelum transaction dimulai IF v_stok IS NULL THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Produk tidak ada'; END IF; IF v_stok < p_qty THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Stok tidak cukup'; END IF; SET v_total = v_harga * p_qty; START TRANSACTION; -- Step 1: Kurangi stok (dengan defensive AND untuk keamanan ekstra) UPDATE produk SET stok = stok - p_qty WHERE produk_id = p_produk_id AND stok >= p_qty; -- defensive check -- Step 2: Buat order baru INSERT INTO orders (customer_id, tanggal, total_harga, status) VALUES (p_customer_id, CURDATE(), v_total, 'PENDING'); SET p_order_id = LAST_INSERT_ID(); -- Step 3: Catat item pesanan INSERT INTO order_items (order_id, produk_id, qty, harga_satuan) VALUES (p_order_id, p_produk_id, p_qty, v_harga); COMMIT; END$$ DELIMITER ; -- Cara pakai: SET @new_order_id = 0; CALL sp_checkout(3, 104, 1, @new_order_id); SELECT @new_order_id AS order_baru;

SAVEPOINT — rollback parsial untuk batch processing

SQL
START TRANSACTION; -- ── Order Customer A ───────────────────────────── SAVEPOINT sp_customer_a; UPDATE produk SET stok = stok - 20 WHERE produk_id = 104 AND stok >= 20; -- stok hanya 15 → 0 baris terupdate -- ROW_COUNT() = 0 → update tidak berhasil karena stok kurang -- Batalkan hanya order Customer A, bukan seluruh transaksi ROLLBACK TO sp_customer_a; -- ↩ kembali ke checkpoint sp_customer_a -- ── Order Customer B (lanjut, tidak ikut dibatalkan) ── SAVEPOINT sp_customer_b; UPDATE produk SET stok = stok - 1 WHERE produk_id = 105 AND stok >= 1; INSERT INTO orders (customer_id, tanggal, total_harga, status) VALUES (5, CURDATE(), 380000, 'PENDING'); INSERT INTO order_items (order_id, produk_id, qty, harga_satuan) VALUES (LAST_INSERT_ID(), 105, 1, 380000); COMMIT; -- hanya order Customer B yang tersimpan -- Catatan penting: -- ROLLBACK TO SAVEPOINT → tidak mengakhiri transaksi, hanya mundur ke checkpoint -- RELEASE SAVEPOINT sp_nama → hapus checkpoint (opsional, otomatis saat COMMIT/ROLLBACK penuh)
Jebakan UAS #4: Soal "jelaskan kenapa checkout harus pakai transaction" → jawabannya harus menyebut Atomicity secara eksplisit + skenario konkret jika salah satu langkah gagal di tengah (stok sudah berkurang, order tidak terbuat).

View & Stored Procedure

View = tabel virtual dari query. Stored Procedure = blok kode SQL yang bisa dipanggil berulang. Keduanya wajib muncul di soal studi kasus.

CREATE VIEW — laporan penjualan bulanan

SQL
-- View merangkum query kompleks jadi "tabel" yang bisa di-query biasa CREATE OR REPLACE VIEW v_laporan_penjualan AS SELECT p.produk_id, p.nama_produk, k.nama_kategori, MONTH(o.tanggal) AS bulan, YEAR(o.tanggal) AS tahun, SUM(oi.qty) AS total_qty_terjual, SUM(oi.qty * oi.harga_satuan) AS total_revenue FROM produk p JOIN kategori k ON p.kategori_id = k.kategori_id JOIN order_items oi ON p.produk_id = oi.produk_id JOIN orders o ON oi.order_id = o.order_id WHERE o.status IN ('COMPLETED', 'PENDING') GROUP BY p.produk_id, p.nama_produk, k.nama_kategori, MONTH(o.tanggal), YEAR(o.tanggal); -- Query view sama persis seperti query tabel biasa: SELECT * FROM v_laporan_penjualan WHERE bulan = 5 ORDER BY total_revenue DESC; -- Produk revenue tertinggi per bulan per kategori (pakai correlated subquery ke view): SELECT v.nama_kategori, v.bulan, v.tahun, v.nama_produk, v.total_revenue FROM v_laporan_penjualan v WHERE v.total_revenue = ( SELECT MAX(v2.total_revenue) FROM v_laporan_penjualan v2 WHERE v2.nama_kategori = v.nama_kategori AND v2.bulan = v.bulan AND v2.tahun = v.tahun ) ORDER BY v.tahun DESC, v.bulan DESC;

Cara baca relasi

  • order_items menyelesaikan relasi N–N antara orders dan produk

01 Essay Jelaskan urutan eksekusi SQL dan mengapa WHERE tidak bisa menyaring hasil aggregate function. ▾
// Soal
Jelaskan urutan eksekusi klausa-klausa SQL berikut secara berurutan: FROM, JOIN, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT. Kemudian berikan contoh query yang salah (menggunakan WHERE dengan aggregate) dan versi yang benar, serta jelaskan mengapa versi salah akan menghasilkan error.

// Pembahasan Lengkap

Urutan eksekusi SQL (bukan urutan penulisan!):

  1. FROM / JOIN — Database menentukan tabel dan melakukan join; menghasilkan working table mentah
  2. WHERE — Menyaring baris mentah; pada titik ini aggregate belum dihitung sama sekali
  3. GROUP BY — Mengelompokkan baris hasil WHERE menjadi grup-grup
  4. HAVING — Menyaring grup berdasarkan kondisi; aggregate sudah tersedia di sini
  5. SELECT — Memilih dan menghitung kolom output; alias kolom lahir di sini
  6. ORDER BY — Mengurutkan hasil (bisa pakai alias dari SELECT)
  7. LIMIT / OFFSET — Membatasi jumlah baris yang dikembalikan ke client
SQL · Perbandingan
-- ❌ SALAH: WHERE tidak bisa menyaring hasil aggregate -- Error: "Invalid use of group function" SELECT customer_id, SUM(total_harga) AS total FROM orders WHERE SUM(total_harga) > 500000 -- ← ERROR! SUM belum ada saat WHERE jalan GROUP BY customer_id; -- ✅ BENAR: pindahkan ke HAVING karena aggregate sudah ada setelah GROUP BY SELECT customer_id, SUM(total_harga) AS total FROM orders WHERE status = 'COMPLETED' -- ← WHERE boleh: filter baris biasa GROUP BY customer_id HAVING SUM(total_harga) > 500000 -- ← HAVING boleh: filter setelah aggregate ORDER BY total DESC; -- alias 'total' bisa dipakai di sini (lahir di SELECT)

Mengapa error? Saat WHERE dieksekusi (langkah 2), mesin database belum mengelompokkan baris (GROUP BY baru di langkah 3) dan belum menghitung aggregate apapun. SUM(total_harga) tidak memiliki nilai yang bisa dibandingkan. Database tidak bisa mengevaluasi kondisi yang merujuk ke sesuatu yang belum ada.

02 Essay Analisis perbedaan Correlated vs Non-Correlated Subquery dari sisi performa dan use case. ▾
// Soal
Jelaskan perbedaan correlated dan non-correlated subquery. Berikan masing-masing satu contoh SQL menggunakan database Toko Online. Analisis mengapa correlated subquery bisa lebih lambat untuk dataset besar, dan kapan tetap perlu digunakan.

// Pembahasan Lengkap

Non-Correlated
  • Tidak merujuk kolom outer query
  • Dieksekusi 1 kali, hasilnya di-cache
  • Kompleksitas: O(1) eksekusi subquery
  • Cocok untuk: perbandingan dengan nilai global (rata-rata semua, max semua)
Correlated
  • Merujuk kolom dari outer query
  • Dieksekusi per baris outer table
  • Kompleksitas: O(n) eksekusi subquery
  • Cocok untuk: "di atas rata-rata grupnya sendiri"
SQL · Non-Correlated
-- Non-Correlated: subquery dieksekusi SEKALI, hasilnya 356000 -- Query luar membandingkan setiap harga dengan 356000 SELECT nama_produk, harga, harga - (SELECT AVG(harga) FROM produk) AS selisih FROM produk WHERE harga > (SELECT AVG(harga) FROM produk); -- Jumlah eksekusi subquery: 2x (sekali per kemunculan di SQL)
SQL · Correlated
-- Correlated: cari customer dengan belanja > rata-rata KATEGORI KOTANYA -- Subquery dieksekusi ULANG untuk tiap baris c (tiap customer) -- Jika ada 1000 customer → subquery jalan 1000x SELECT c.nama, c.kota FROM customers c WHERE (SELECT SUM(o.total_harga) FROM orders o WHERE o.customer_id = c.customer_id -- ← referensi outer! AND o.status = 'COMPLETED') > (SELECT AVG(total_per_kota) FROM (SELECT SUM(o2.total_harga) AS total_per_kota FROM orders o2 JOIN customers c2 ON o2.customer_id = c2.customer_id WHERE c2.kota = c.kota -- ← juga correlated! AND o2.status = 'COMPLETED' GROUP BY c2.customer_id) sub);

Kapan tetap pakai correlated? Saat perbandingan harus dilakukan terhadap nilai yang bergantung pada data baris itu sendiri — misalnya "di atas rata-rata kategorinya" atau "produk yang terjual lebih dari stok awalnya". Di MySQL 8.0+, window function seperti AVG() OVER (PARTITION BY ...) bisa menggantikan correlated subquery dengan performa jauh lebih baik.

03 Essay Jelaskan BEFORE vs AFTER trigger — kapan WAJIB pakai masing-masing dan konsekuensi salah pilih timing. ▾
// Soal
Jelaskan perbedaan timing BEFORE dan AFTER pada trigger MySQL secara konseptual. Berikan satu skenario nyata di sistem toko online yang wajib menggunakan BEFORE dan satu yang wajib menggunakan AFTER. Jelaskan konsekuensi jika timing dipilih terbalik.

// Pembahasan Lengkap

BEFORE Trigger
  • Jalan sebelum data tersimpan ke tabel
  • Bisa modifikasi NEW.kolom (normalisasi data)
  • Bisa tolak dengan SIGNAL → data tidak pernah masuk
  • Tujuan: validasi & sanitasi input
AFTER Trigger
  • Jalan setelah data berhasil tersimpan
  • Tidak bisa modifikasi NEW (sudah terlanjur masuk)
  • Punya akses ke ID baru (AUTO_INCREMENT sudah di-assign)
  • Tujuan: efek samping (update tabel lain, logging)

Skenario WAJIB BEFORE — Validasi Stok: Kita harus mencegah baris order_items masuk jika stok tidak cukup. Kalau pakai AFTER, data sudah terlanjur tersimpan ke order_items sebelum kita bisa cek → database dalam state inkonsisten walau SIGNAL akhirnya membatalkan transaksi.

Skenario WAJIB AFTER — Logging Transaksi: Kita perlu mencatat ke tabel log dengan menyertakan order_item_id yang baru di-insert. ID ini (AUTO_INCREMENT) baru tersedia setelah INSERT selesai. Kalau pakai BEFORE, ID belum di-assign → log akan berisi ID yang salah atau NULL.

Konsekuensi salah timing: AFTER untuk validasi → data masuk dulu baru ditolak (state inkonsisten sesaat). BEFORE untuk logging dengan NEW.id → ID belum ada, logging rusak. Keduanya menghasilkan bug yang sulit dideteksi.
04 Essay Analisis skenario checkout tanpa Transaction — ACID mana yang dilanggar dan apa dampaknya? ▾
// Soal
Seorang developer menulis kode checkout tanpa SQL Transaction. Server mati setelah UPDATE stok berhasil tetapi sebelum INSERT orders. Identifikasi properti ACID mana yang dilanggar, jelaskan dampak konkretnya terhadap data, dan implementasikan solusi yang benar.

// Pembahasan Lengkap

Skenario kegagalan:

Timeline Kegagalan
✓ Step 1: UPDATE produk SET stok = stok - 1 WHERE produk_id = 104; → stok berkurang dari 15 → 14. Tersimpan di disk. ✗ [SERVER CRASH / KONEKSI PUTUS] ✗ Step 2: INSERT INTO orders ... → TIDAK PERNAH DIEKSEKUSI ✗ Step 3: INSERT INTO order_items ... → TIDAK PERNAH DIEKSEKUSI -- Kondisi akhir database: -- produk_id=104: stok=14 (berkurang 1, padahal tidak ada order) -- orders: tidak ada order baru -- order_items: tidak ada data baru -- Customer sudah bayar tapi order tidak terbuat → chaos!

ACID yang dilanggar:

  • ❌ Atomicity — Operasi tidak diperlakukan sebagai satu unit; hanya sebagian yang tersimpan
  • ❌ Consistency — Database jatuh ke state tidak valid: stok berkurang tapi order tidak ada
  • ✅ Isolation — Tidak relevan langsung (masalah di single-user scenario)
  • ✅ Durability — Yang sempat di-commit memang persisten, tapi inilah masalahnya
SQL · Solusi Benar
START TRANSACTION; UPDATE produk SET stok = stok - 1 WHERE produk_id = 104 AND stok >= 1; INSERT INTO orders (customer_id, tanggal, total_harga, status) VALUES (3, CURDATE(), 620000, 'PENDING'); INSERT INTO order_items (order_id, produk_id, qty, harga_satuan) VALUES (LAST_INSERT_ID(), 104, 1, 620000); COMMIT; -- semua berhasil → tersimpan permanen -- Jika ada error di mana pun antara START TRANSACTION dan COMMIT: -- ROLLBACK; → semua langkah dibatalkan, stok kembali ke 15

Dengan Transaction, jika server mati setelah UPDATE stok tetapi sebelum COMMIT, database akan otomatis me-rollback semua perubahan saat server restart (melalui redo log) — memastikan Atomicity terjaga.

05 Studi Kasus Laporan penjualan per kategori — JOIN + GROUP BY + HAVING + multiple aggregate. ▾
// Soal
Tampilkan nama kategori, jumlah produk dalam kategori, rata-rata harga produk, produk termahal, dan total unit produk yang pernah terjual. Hanya tampilkan kategori yang rata-rata harganya di atas 250.000 dan memiliki minimal 2 produk. Urutkan dari rata-rata harga tertinggi.

// Jawaban & Penjelasan

SQL
SELECT k.nama_kategori, COUNT(p.produk_id) AS jumlah_produk, ROUND(AVG(p.harga), 0) AS rata_harga, MAX(p.harga) AS harga_termahal, COALESCE(SUM(oi.qty), 0) AS total_unit_terjual FROM kategori k JOIN produk p ON p.kategori_id = k.kategori_id LEFT JOIN order_items oi ON oi.produk_id = p.produk_id GROUP BY k.kategori_id, k.nama_kategori HAVING AVG(p.harga) > 250000 AND COUNT(p.produk_id) >= 2 ORDER BY rata_harga DESC;
// Penjelasan per klausa
KlausaPenjelasan
JOIN produkINNER JOIN — hanya kategori yang punya produk yang muncul
LEFT JOIN order_itemsLEFT karena produk yang belum pernah terjual tetap harus muncul (qty-nya jadi NULL)
COALESCE(SUM(oi.qty), 0)NULL dari LEFT JOIN yang tidak punya pasangan diubah jadi 0
GROUP BY k.kategori_id, k.nama_kategoriWajib sertakan semua kolom non-aggregate di GROUP BY
HAVING AVG(...) > 250000 AND COUNT(...) >= 2Dua kondisi aggregate — keduanya wajib di HAVING, bukan WHERE
ORDER BY rata_harga DESCAlias yang lahir di SELECT bisa dipakai di ORDER BY
Hasil dengan data dummy: Kategori Elektronik (3 produk, rata-rata 326.667, max 450.000) ✅ muncul. Fashion (1 produk) dan Olahraga (1 produk) tidak muncul karena COUNT < 2.
06 Studi Kasus Laporan customer lengkap — JOIN 3 tabel + scalar subquery + perbandingan vs rata-rata. ▾
// Soal
Tampilkan nama customer, jumlah order COMPLETED, total belanja (dihitung dari qty × harga_satuan di order_items), dan selisih total belanjanya dibanding rata-rata belanja semua customer. Urutkan dari total belanja terbesar.

// Jawaban & Penjelasan

SQL
SELECT c.nama, c.kota, COUNT(DISTINCT o.order_id) AS jumlah_order_completed, SUM(oi.qty * oi.harga_satuan) AS total_belanja, ROUND( SUM(oi.qty * oi.harga_satuan) - (SELECT AVG(total_per_c) FROM ( SELECT SUM(oi2.qty * oi2.harga_satuan) AS total_per_c FROM customers c2 JOIN orders o2 ON o2.customer_id = c2.customer_id JOIN order_items oi2 ON oi2.order_id = o2.order_id WHERE o2.status = 'COMPLETED' GROUP BY c2.customer_id ) avg_sub) , 0) AS selisih_dari_rata FROM customers c JOIN orders o ON o.customer_id = c.customer_id AND o.status = 'COMPLETED' -- filter di ON, lebih efisien dari WHERE JOIN order_items oi ON oi.order_id = o.order_id GROUP BY c.customer_id, c.nama, c.kota ORDER BY total_belanja DESC;
// Poin kritis yang dinilai dosen
  • SUM(oi.qty * oi.harga_satuan) lebih akurat dari SUM(o.total_harga) karena dihitung dari detail aktual
  • COUNT(DISTINCT o.order_id) — DISTINCT penting agar tidak double-count dari JOIN ganda
  • Scalar subquery di SELECT (non-correlated): dieksekusi sekali, hasilnya dipakai berulang untuk tiap baris
  • Filter o.status = 'COMPLETED' di ON clause JOIN (bukan WHERE) agar customer tanpa order COMPLETED tidak hilang dari hasil
07 Studi Kasus Produk belum pernah terjual — NOT EXISTS vs NOT IN, dan IN bertingkat 4 level. ▾
// Soal
(a) Tampilkan produk yang belum pernah dipesan menggunakan NOT EXISTS. (b) Tampilkan customer yang pernah membeli produk dari kategori 'Elektronik' menggunakan subquery IN bertingkat (tanpa JOIN).

// Jawaban & Penjelasan

SQL · Part A — NOT EXISTS
-- NOT EXISTS: cek "tidak ada baris di order_items untuk produk ini" -- Lebih aman dari NOT IN ketika kolom bisa mengandung NULL SELECT p.produk_id, p.nama_produk, p.stok FROM produk p WHERE NOT EXISTS ( SELECT 1 -- nilai '1' tidak penting, hanya cek ada baris atau tidak FROM order_items oi WHERE oi.produk_id = p.produk_id -- ← ini correlated (merujuk p dari luar) );
SQL · Part B — IN Bertingkat 4 Level
-- IN bertingkat: dari customer_id → order_id → produk_id → kategori_id SELECT DISTINCT c.nama, c.email FROM customers c WHERE c.customer_id IN ( -- Level 2: customer_id dari order yang berisi produk Elektronik SELECT o.customer_id FROM orders o WHERE o.order_id IN ( -- Level 3: order_id yang berisi produk Elektronik SELECT oi.order_id FROM order_items oi WHERE oi.produk_id IN ( -- Level 4: produk_id yang masuk kategori Elektronik SELECT p.produk_id FROM produk p WHERE p.kategori_id = ( -- Level 5: cari kategori_id untuk 'Elektronik' SELECT k.kategori_id FROM kategori k WHERE k.nama_kategori = 'Elektronik' ) ) ) ); -- Versi JOIN yang ekuivalen (lebih efisien untuk dataset besar): SELECT DISTINCT c.nama, c.email FROM customers c JOIN orders o ON o.customer_id = c.customer_id JOIN order_items oi ON oi.order_id = o.order_id JOIN produk p ON p.produk_id = oi.produk_id JOIN kategori k ON k.kategori_id = p.kategori_id WHERE k.nama_kategori = 'Elektronik';
Mengapa NOT EXISTS lebih aman dari NOT IN? Jika subquery NOT IN menghasilkan set yang mengandung NULL, seluruh kondisi NOT IN menjadi FALSE (karena NULL != apapun). NOT EXISTS tidak terpengaruh NULL karena hanya cek ada/tidaknya baris.
08 Studi Kasus Trigger BEFORE INSERT — validasi stok berlapis + normalisasi harga_satuan otomatis. ▾
// Soal
Buat trigger pada tabel order_items yang: (1) mencegah insert jika qty melebihi stok, (2) mencegah insert jika produk tidak ditemukan, (3) mencegah qty negatif atau nol, dan (4) secara otomatis mengisi kolom harga_satuan dengan harga dari tabel produk. Jelaskan timing yang dipilih.

// Jawaban & Penjelasan

SQL · BEFORE INSERT Trigger
DELIMITER $$ CREATE TRIGGER trg_validasi_order_items BEFORE INSERT ON order_items -- BEFORE: karena kita ingin CEGAH data masuk FOR EACH ROW BEGIN DECLARE v_stok_tersedia INT; DECLARE v_harga_produk DECIMAL(12,2); -- Step 1: Ambil data produk dari tabel produk SELECT stok, harga INTO v_stok_tersedia, v_harga_produk FROM produk WHERE produk_id = NEW.produk_id; -- Validasi 1: produk harus ada di database IF v_stok_tersedia IS NULL THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'ERROR: Produk tidak ditemukan di database'; END IF; -- Validasi 2: qty harus bilangan positif IF NEW.qty <= 0 THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'ERROR: Qty pesanan harus lebih dari 0'; END IF; -- Validasi 3: stok harus mencukupi IF NEW.qty > v_stok_tersedia THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'ERROR: Qty pesanan melebihi stok yang tersedia'; END IF; -- Normalisasi: timpa harga_satuan dengan harga resmi dari tabel produk -- Ini mencegah manipulasi harga dari sisi client -- SET NEW.kolom HANYA bisa dilakukan di BEFORE trigger, bukan AFTER SET NEW.harga_satuan = v_harga_produk; END$$ DELIMITER ; -- Test 1: Qty melebihi stok (stok=10, beli 99) → harus error INSERT INTO order_items (order_id, produk_id, qty, harga_satuan) VALUES (1001, 105, 99, 0); -- Expected: ERROR 45000: Qty pesanan melebihi stok yang tersedia -- Test 2: Order normal INSERT INTO order_items (order_id, produk_id, qty, harga_satuan) VALUES (1003, 105, 1, 0); -- Expected: sukses, harga_satuan otomatis terisi 380000 dari trigger

Alasan BEFORE: Keempat tujuan trigger ini adalah mencegah data buruk masuk dan menormalisasi nilai. Keduanya hanya bisa dilakukan sebelum data tersimpan (BEFORE). Jika pakai AFTER, data yang tidak valid sudah terlanjur masuk ke tabel sebelum bisa ditolak — ini menghasilkan race condition dalam error handling.

09 Studi Kasus Trigger AFTER UPDATE — restore stok + logging saat order di-cancel. ▾
// Soal
Definisikan tabel order_log terlebih dahulu, lalu buat trigger yang aktif saat status order berubah dari PENDING menjadi CANCELLED: mengembalikan stok semua produk terkait dan mencatat perubahan ke order_log.

// Jawaban & Penjelasan

SQL
-- Langkah 1: Buat tabel log CREATE TABLE order_log ( log_id INT PRIMARY KEY AUTO_INCREMENT, order_id INT NOT NULL, aksi VARCHAR(50), old_status VARCHAR(20), new_status VARCHAR(20), keterangan TEXT, waktu DATETIME DEFAULT CURRENT_TIMESTAMP ); -- Langkah 2: Buat AFTER UPDATE trigger pada orders DELIMITER $$ CREATE TRIGGER trg_cancel_order AFTER UPDATE ON orders -- AFTER: data sudah berubah, kita bereaksi FOR EACH ROW BEGIN -- Kondisi: hanya proses jika status berubah PENDING → CANCELLED -- OLD = nilai sebelum UPDATE, NEW = nilai setelah UPDATE IF OLD.status = 'PENDING' AND NEW.status = 'CANCELLED' THEN -- Kembalikan stok semua produk dalam order ini sekaligus (satu UPDATE) UPDATE produk p JOIN order_items oi ON p.produk_id = oi.produk_id SET p.stok = p.stok + oi.qty WHERE oi.order_id = NEW.order_id; -- Catat ke log: OLD dan NEW tersedia di seluruh body trigger INSERT INTO order_log (order_id, aksi, old_status, new_status, keterangan) VALUES ( NEW.order_id, 'CANCEL_RESTOCK', OLD.status, NEW.status, CONCAT('Stok dikembalikan. Total order: Rp ', FORMAT(NEW.total_harga, 0, 'id_ID')) ); END IF; END$$ DELIMITER ; -- Test: batalkan order 1007 (status: PENDING) UPDATE orders SET status = 'CANCELLED' WHERE order_id = 1007; -- Verifikasi: stok produk 101 dan 104 harus naik masing-masing 1 SELECT produk_id, stok FROM produk WHERE produk_id IN (101, 104); SELECT * FROM order_log ORDER BY log_id DESC LIMIT 1;

Alasan AFTER: Kita membutuhkan konfirmasi bahwa perubahan status berhasil tersimpan sebelum melakukan efek samping (restore stok dan logging). Kalau BEFORE, dan ada error lain yang mencegah UPDATE orders tersimpan, kita sudah salah restore stok padahal pembatalan tidak jadi terjadi.

10 Studi Kasus Transaction dengan SAVEPOINT — batch checkout 2 customer, salah satu gagal tidak ganggu yang lain. ▾
// Soal
Simulasikan batch checkout: Customer 4 (Budi) memesan 20 unit Sepatu Lari (stok hanya 15 — pasti gagal), dan Customer 5 (Arief) memesan 1 unit Headphone BT. Implementasikan menggunakan SAVEPOINT agar kegagalan Budi tidak membatalkan order Arief.

// Jawaban & Penjelasan

SQL · SAVEPOINT
START TRANSACTION; -- ── BATCH ITEM 1: Budi order 20 Sepatu Lari ────────────────── SAVEPOINT sp_budi; -- Coba kurangi stok: kondisi AND stok >= 20 akan gagal (stok=15) UPDATE produk SET stok = stok - 20 WHERE produk_id = 104 AND stok >= 20; -- ROW_COUNT() = 0 → tidak ada baris yang terupdate → stok tidak cukup -- Di stored procedure: IF ROW_COUNT() = 0 THEN ROLLBACK TO sp_budi ROLLBACK TO SAVEPOINT sp_budi; -- ↩ Semua perubahan sejak SAVEPOINT sp_budi dibatalkan -- TRANSAKSI MASIH AKTIF, belum di-rollback penuh -- ── BATCH ITEM 2: Arief order 1 Headphone BT ───────────────── SAVEPOINT sp_arief; UPDATE produk SET stok = stok - 1 WHERE produk_id = 105 AND stok >= 1; -- stok Headphone=10 → cukup, ROW_COUNT() = 1 → sukses INSERT INTO orders (customer_id, tanggal, total_harga, status) VALUES (5, CURDATE(), 380000, 'PENDING'); INSERT INTO order_items (order_id, produk_id, qty, harga_satuan) VALUES (LAST_INSERT_ID(), 105, 1, 380000); -- Semua sukses → simpan permanen COMMIT; -- ── Verifikasi Hasil ────────────────────────────────────────── SELECT produk_id, nama_produk, stok FROM produk WHERE produk_id IN (104, 105); -- produk 104 (Sepatu Lari): stok TETAP 15 (rollback berhasil) -- produk 105 (Headphone BT): stok = 9 (berkurang 1)
// Mekanisme SAVEPOINT
PerintahEfek
SAVEPOINT namaBuat checkpoint di tengah transaksi aktif
ROLLBACK TO SAVEPOINT namaBatalkan hanya operasi sejak checkpoint tersebut; transaksi masih aktif
RELEASE SAVEPOINT namaHapus checkpoint (opsional; otomatis terhapus saat COMMIT/ROLLBACK)
COMMITSimpan semua perubahan yang belum di-rollback
ROLLBACK (penuh)Batalkan semua perubahan sejak START TRANSACTION
11 Studi Kasus Ranking produk dalam kategori — correlated subquery vs RANK() window function. ▾
// Soal
Tampilkan setiap produk beserta rankingnya dalam kategori masing-masing berdasarkan total qty terjual (produk terlaris = rank 1). Berikan dua solusi: satu menggunakan correlated subquery, satu menggunakan window function RANK().

// Jawaban & Penjelasan

SQL · Solusi 1 — Correlated Subquery
-- Ranking dihitung dengan: hitung berapa produk dalam kategori yang -- penjualannya LEBIH BANYAK dari produk ini → itulah rankingnya SELECT p.nama_produk, k.nama_kategori, COALESCE(SUM(oi.qty), 0) AS total_terjual, ( SELECT COUNT(DISTINCT p2.produk_id) + 1 FROM produk p2 LEFT JOIN order_items oi2 ON p2.produk_id = oi2.produk_id WHERE p2.kategori_id = p.kategori_id -- sama kategori GROUP BY p2.produk_id HAVING COALESCE(SUM(oi2.qty), 0) > COALESCE(SUM(oi.qty), 0) -- terjual lebih banyak ) AS rank_dalam_kategori FROM produk p JOIN kategori k ON p.kategori_id = k.kategori_id LEFT JOIN order_items oi ON p.produk_id = oi.produk_id GROUP BY p.produk_id, p.nama_produk, k.nama_kategori, p.kategori_id ORDER BY k.nama_kategori, rank_dalam_kategori;
SQL · Solusi 2 — Window Function RANK() (MySQL 8.0+)
-- Jauh lebih clean dan efisien dari correlated subquery -- PARTITION BY = reset ranking untuk tiap kategori -- ORDER BY ... DESC = produk paling banyak terjual mendapat rank 1 SELECT p.nama_produk, k.nama_kategori, COALESCE(SUM(oi.qty), 0) AS total_terjual, RANK() OVER ( PARTITION BY p.kategori_id -- ranking per kategori ORDER BY COALESCE(SUM(oi.qty), 0) DESC -- dari terbanyak ) AS rank_dalam_kategori FROM produk p JOIN kategori k ON p.kategori_id = k.kategori_id LEFT JOIN order_items oi ON p.produk_id = oi.produk_id GROUP BY p.produk_id, p.nama_produk, k.nama_kategori, p.kategori_id ORDER BY k.nama_kategori, rank_dalam_kategori; -- Catatan: RANK() memberikan rank yang sama untuk nilai yang sama -- dan melompati angka berikutnya (1, 1, 3, 4 ...) -- ROW_NUMBER() tidak ada lompatan tapi tidak menangani nilai sama -- DENSE_RANK() sama nilai = sama rank, tapi tidak ada lompatan (1, 1, 2, 3)
12 Bonus View + Stored Procedure lengkap — transfer stok antar produk dengan error handling penuh. ▾
// Soal Bonus
Buat stored procedure sp_transfer_stok(dari, ke, jumlah) yang memindahkan stok dari satu produk ke produk lain. Procedure harus: validasi stok mencukupi, validasi produk tidak sama, gunakan transaction, gunakan FOR UPDATE untuk hindari race condition, dan catat ke order_log.

// Jawaban & Penjelasan

SQL · Stored Procedure + Transaction
DELIMITER $$ CREATE PROCEDURE sp_transfer_stok( IN p_dari INT, -- produk_id sumber IN p_ke INT, -- produk_id tujuan IN p_jml INT -- jumlah unit yang dipindah ) BEGIN DECLARE v_stok_dari INT DEFAULT 0; DECLARE v_stok_ke INT DEFAULT 0; DECLARE v_nama_dari VARCHAR(200); DECLARE v_nama_ke VARCHAR(200); -- EXIT HANDLER: tangkap semua SQL error, rollback lalu teruskan error DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN ROLLBACK; RESIGNAL; END; -- Validasi parameter sebelum membuka transaction IF p_jml <= 0 THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Jumlah transfer harus lebih dari 0'; END IF; IF p_dari = p_ke THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Produk sumber dan tujuan tidak boleh sama'; END IF; START TRANSACTION; -- Kunci dua baris sekaligus dengan FOR UPDATE (pessimistic locking) -- Ini mencegah dua transfer berjalan bersamaan ke produk yang sama SELECT stok, nama_produk INTO v_stok_dari, v_nama_dari FROM produk WHERE produk_id = p_dari FOR UPDATE; -- kunci baris ini sampai COMMIT/ROLLBACK SELECT stok, nama_produk INTO v_stok_ke, v_nama_ke FROM produk WHERE produk_id = p_ke FOR UPDATE; -- kunci baris ini juga -- Cek produk ada IF v_nama_dari IS NULL THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Produk sumber tidak ditemukan'; END IF; IF v_nama_ke IS NULL THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Produk tujuan tidak ditemukan'; END IF; -- Cek stok mencukupi IF v_stok_dari < p_jml THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Stok sumber tidak mencukupi untuk transfer'; END IF; -- Lakukan transfer stok UPDATE produk SET stok = stok - p_jml WHERE produk_id = p_dari; UPDATE produk SET stok = stok + p_jml WHERE produk_id = p_ke; -- Log ke order_log INSERT INTO order_log (order_id, aksi, keterangan) VALUES (0, 'TRANSFER_STOK', CONCAT('Transfer ', p_jml, ' unit dari [', v_nama_dari, '] ke [', v_nama_ke, ']')); COMMIT; -- Kembalikan summary ke pemanggil SELECT v_nama_dari AS produk_sumber, v_stok_dari AS stok_sumber_sebelum, v_stok_dari - p_jml AS stok_sumber_sesudah, v_nama_ke AS produk_tujuan, v_stok_ke AS stok_tujuan_sebelum, v_stok_ke + p_jml AS stok_tujuan_sesudah, p_jml AS jumlah_transfer, 'SUCCESS' AS status; END$$ DELIMITER ; -- Cara pakai: pindah 5 unit Keyboard Mekanik (101) ke Mouse Wireless (102) CALL sp_transfer_stok(101, 102, 5);
FOR UPDATE — Pessimistic Locking: Saat dua sesi database mencoba transfer stok ke produk yang sama secara bersamaan, FOR UPDATE memastikan salah satunya harus menunggu sampai yang pertama COMMIT atau ROLLBACK. Tanpa ini, bisa terjadi race condition di mana kedua sesi membaca stok yang sama (misal 20) lalu keduanya mengurangi stok — hasilnya stok bisa jadi negatif.
